# Working rules

Operating procedures for agents in this repository. They follow the current tools and layout and change with them. The owner's intent and decision rules are in `AGENTS.md`.

Use idle tasks for work planning and the active goal for the objective. The 50 cm ape-shaped robot is the target; earlier 35 cm work is historical evidence. Microduck, Microban, and Berkeley are references. Use upstream Arena, Isaac Lab, Mimic, LeRobot, and GR00T code where relevant. Work locally in this folder; Runpod is compute only.

`robot/design.json` names the selected design: `selected` maps each robot section to its one selected study, and one study may cover several sections. Use its exact source when continuing; record a new selection with `infra/dashboard/results_hub.py select-design STUDY_ID --robot-section SECTION` and in Idle. Selection does not imply physical or learned-control qualification.

This is a disposable learning POC. Running the workflow is the test; do not add broad test coverage. Delete abandoned experiments when useful.

Git holds versions; file names never do. Edit a file and commit instead of creating `_v2`, `-r3`, `final` or dated copies, and name files by content. Process records (reviews, authorizations, verifications, receipts, handoffs, locks, logs, input snapshots) go to the Git-ignored `.bookkeeping/` folder, not `data/`. Research is one document per topic in `docs/research/`, updated in place with results; never a note per run. See `docs/operations/git-and-bookkeeping.md`; `.githooks/pre-commit` enforces the names (`git config core.hooksPath .githooks`).

The blob store, the private archive and the dashboards hold source of truth only: code and CAD sources in Git, external inputs that cannot be fetched again, and the current state the dashboards show (the selected design per section, the newest version of each skill with its clip) (owner, 2026-11-17). Everything else is recreated by running its script or its training when someone needs it, and is deleted at the end of the task from local disk and remote storage. Never upload derived outputs as backups. When a piece of work depends on something that cannot be recreated from a script, that is a defect: refactor it into a script plus its inputs while working on it.

Keep a lean local checkout: code, compact records and actual in-progress inputs. About 10 GB is a rough expectation, not an exact cap; preserve necessary working inputs and runtimes. Put temporary working materializations in `.cache/` or a temporary directory and evict them when the work ends. Remove unused reproducible tool installations and environments while keeping their pinned setup instructions. Do not retain historical run or design folders, locally or in object storage.

New producers must separate cheap derived output in `LAB_WORK_DIR` (`.cache/work/<run-id>/`) from retained native evidence in `LAB_EVIDENCE_DIR` (`artifacts/runs/<run-id>/`). Run them with `infra/lab storage run NAME -- COMMAND`, using `{work}` and `{evidence}` arguments or those environment variables. The wrapper records the exact command, seals completed evidence, hash-verifies private storage and evicts unchanged bulk automatically; successful scratch is disposable. Keep required inputs and compact configurations/reports outside scratch. Existing producers close one explicitly completed run with `infra/lab storage finish artifacts/EXACT_RUN` or `results_hub.py publish RECORD.json --close-run artifacts/EXACT_RUN`. Never close a run that still supplies active native inputs. `infra/lab storage sync` retries queued offloads; `clean` removes only declared completed scratch, never arbitrary `.cache` contents. See `docs/operations/storage-lifecycle.md`.

No simulation, training, evaluation rollouts or smoke tests run on the local CPU (owner, 2026-11-12). Smoke tests are short GPU jobs on the existing bounded serverless path, with their own spend reflection. Local work is code, reading, and analysis or renders of traces that already exist. Historical notes that describe "local CPU" checks are provenance, not a procedure to repeat. CAD verification (static FEM and kinematic collision sweeps) is the exception: it runs locally under `infra/tools/memguard.py` (owner, 2026-11-12).

CAD design loop (2026-11-18). One shared design check, `robot/body/checks/run.py`, replaces the per-study check scripts. Each design iteration runs it scoped to what changed and shows the owner a candidate only together with its findings; the whole body runs once before release to print. Run one heavy job at a time (`pgrep -fl memguard` first), always under memguard, so that a hang stops with a message. Use a fresh agent for each CAD step and don't resume a long one. Run long steps in the background and wait for the completion notice:

`python3 infra/tools/memguard.py --limit-gb 6 --timeout-s 900 -- .venv/bin/python -B robot/body/checks/run.py [--manifest PATH] [scope] [--checks a,b,c]`

`--manifest` is the body to check; without it the run uses `body_manifest` in `robot/design.json` (the selected body, today `artifacts/robot/body/ape-proportions/shell-pass/assembly-parts-roll-flip.json`). Scope narrows the parts and combines with AND; none = every non-hardware part: `--parts NAME,GLOB` (part names or globs), `--section Hip` (robot section; the table `robot/body/checks/data/sections.json` maps sections to links), `--link GLOB` (owning link), `--role ROLE`, `--changed-since REV|last-run` (Git revision, or file sha256 since the previous run on this manifest). The scoped parts are checked against their neighbours (close over the pose set or touching at standing), not against the whole body. `--checks` named = only those; none = every check that applies to the scope. `--list-checks` prints them. `--poses key|library|all|fit` picks the pose set (named data in `robot/body/checks/data/pose_sets.json`: key 23 key / extreme poses, library 151 realistic poses, all 223, fit the exact-fit list). Those are leg-motion sets; parts on an arm, neck or torso link get that region's own poses instead (`region_poses` in the same file: each joint at both ends of its manifest range, named combinations; `library` / `all` add the chain's corner combinations: arm 14 / 30 poses, neck 5 / 9, torso 30 / 42; a scope mixing leg and region parts gets both). The result is one JSON report, `.cache/work/cad-speed/checks/<label>/report.json` (`--label`), and a short worst-first summary on stdout: per check, per part, measurements in native units, worst cases with pose / location / mating part, counts of bad events, seconds. Lines that are context without a finding (the bed margin of a part that fits, STEP-vs-mesh volume difference) are kept in the report and only counted in the summary. Setup timers (solids, neighbours) are repeated in every child process and reported apart (`setup_seconds_summed_over_children`), so `seconds` does not add them to the checks. `--changed-since last-run` names why a part was selected (`neighbour_changed: <part>` or `neighbour_never_recorded: <part>`). Nothing is pass or fail.

|---|---|---|

| `mass` | solid volume x the part's material density vs the manifest mass; owning link mass and COM | under 2 |
| `gaps` | standing overlap (mm3) and distance (mm) of every part within 6 mm of a scoped part | 4-28 |
| `static_audit` | standing overlap volume of each scoped part against every other non-fastener part (exact mesh booleans) | 3 |
| `clearance` | new overlap vs standing (mm3) and minimum distance (mm) against neighbours on other links over the pose set | 15-25 on 2 parts at `key`, 140 at `library`, 430 at `all` |
| `fit` | exact B-rep overlap and minimum distance over the pose set (use `--poses fit`) | 320 on the two roll-flip connectors |
| `press` | steel sleeves: press tool path obstruction (mm3); counter side as a spacer block: exit-plane contact shares flat / wall (integral wall) / recess / open (%), support = flat + wall, free spacer depth along the axis (mm); the old fixed dia 20 x 40 post volume, coverage (%) and flatness (mm) stay reported; `--exact-press` uses the exact OCC booleans (logic in `checks/press_lib.py`) | 0.2-16 |
| `range_sweep`, `collision_sweep` | per joint that moves a scoped part: first-contact angle each side and overlap against angle / pair overlap and clearance over the joint range with neighbouring joints | 50 / 90 on 2 parts |
| `shell_offset` | inner-wall distance of a cover shell from the parts it covers | 2 |
| `render` | the owner six-side case drawing of the manifest | 10 |
| `fem` | static FEM of every scoped part that has a setup: p99 / peak von Mises, p99 layer tension, in-plane and across-layer strength ratio, displacement per load case, per material; the layer normal is the part's print direction (`process.up`), `--fem-variant studied_axes` runs the stored `layer_normal_axes` instead | 4-100 per part at the stored mesh (h 2.2 mm), up to 2300 on the fine meshes of convergence runs |
| `fem_setup` | the setup against the current part: per patch area, nodes, mating part and holes it lands on, reaction equals minus the wrench; lists printed parts in scope without a setup (coverage: connectors, carriers and body shells); per part its print direction and source, and counts of parts with a setup whose print direction is missing (FEM falls back to the stored axes), seeded (unconfirmed) or not among the stored `layer_normal_axes` | 0.3-5 per part |
| `print_setup` | resolved print setup per printed part (printer, material, nozzle, layer height, line width, up direction) with the source of each value, and coverage: printed parts without direction / material / STEP, seeded values not yet confirmed | under 1 |
| `overhang` | per printed part in its print direction: downward area by overhang angle (from vertical), area beyond the material's limit, flat-ceiling bridge spans to the nearest supported edge (floating ceilings flagged), beyond-limit area on mating faces at standing | 1-15 per part |
| `walls` | per printed part: wall thickness and gap width by ray casting against its line width (one line, two lines), thinnest spots with locations | 0.1-3 per part |
| `bed` | first layer per printed part in its print direction: contact area and islands, share of the footprint, thin contact strips, sharp outline corners, aspect, centre of mass inside / outside the contact hull | under 2 per part |
| `small_features` | per printed part in its print direction: free-standing pins / ribs per layer narrower than two line widths, plan-overlapping flat faces closer than one layer height, internal voids, support standing on the part | 0.3-2 per part |
| `holes` | per printed part, holes from the STEP: diameter, depth, axis vs print direction; sleeve press interference (CAD and after the printer's coupon hole offset); screw hole as pilot (% of thread major) or clearance; boss wall around hardware holes | under 1 per part |
| `bom` | manifest-wide: the generated robot BOM (`robot/body/bom/build.py`) against the CAD: lines whose `lines.json` quantity differs from the CAD count, buy lines without supplier, open make / buy, number of screw / nut / washer / spacer kinds and sleeve sizes, per-part gaps a builder hits (mesh only, file missing, no print settings, no assembly step) | 2-5 (about 60 more when the hardware specs must be measured) |
| `slicer` | Bambu Studio headless per printed part in its print direction with the system profiles of its printer, nozzle and material (support on): return code and warnings, print time, filament and support grams, layers, bridge time; profile hashes and slicer version recorded. Needs the app in `.tools/bambu-studio-2.8.2.61/` (restore the DMG with `infra/storage/restore_native_tool.py bambu`, copy BambuStudio.app out of it) | 2-5 per part |
| `edges` | per printed part, every sharp B-rep edge (dihedral, length, location, convex / concave, free or on a mating face), sharp corners, smallest fillet and chamfer; a picture per part with the sharp edges marked | 2-4 per part |
| `connectivity` | manifest-wide connection graph (screw, sleeve, joint, contact edges): isolated parts, groups not reaching the core, the contact-only break points on the chains to the core, per scoped part its chain | 30-60 (loads every solid) |

Own child process | 8-20 |
| `fastener_motion` | every screw of the scoped links or touching a scoped part (head, shank, last 3 mm tip) against the non-fastener parts on other links over the pose set (`--joints J` adds the range poses of that joint, `--step-deg`): overlap mm3 split head / shank / tip with the worst pose and location, the full-mesh overlap at that pose, minimum distance mm; and screws whose head sits in a same-link part or steel sleeve at standing (mm3, stale screw models) | 5-10 on the roll-flip thigh connector |
| `driver_access` | per screw touching the scope, at standing: a cylinder of the driver's blade diameter along the axis from the head outward (`data/tools.json`: drive per head type and thread, blade diameters labelled assumption) to the exit of the body's box (40-250 mm): obstruction volume (mm3, whole path and first 40 mm), share of the path, first obstructing part and its distance from the head | 3-10 |
| `assembly` | walks `data/assembly_order.json` (ordered steps per subassembly): per part step the straight insertion path (1 mm samples to 60 mm) against the parts assembled earlier: first contact distance (mm), max overlap (mm3), overlap left at 60 mm, seat overlap; per screw step the driver path against what is assembled at that step (mm3, first distance), the later parts that close it in, parts it touches not yet placed; coverage of parts / screws on the assembly's links that no step names. Runs the assemblies that name a scoped part; all steps are seeded drafts until confirmed | 15 on the right leg (43 steps) |
| `heat` | per printed part at standing, against every heat source (servo case / motor, battery cell, power board; `data/heat_sources.json`, each temperature labelled with its source or as an assumption): contact area (mm2), closest distance (mm), area within 3 mm, the source's worst-case temperature, the part's material HDT (0.45 / 1.8 MPa) and Tg and the margin in C; counts of parts in contact / within 3 mm. `--process material=...` changes the margins | 10-20 per part |

Editing the assembly order: `robot/body/checks/data/assembly_order.json`, `assemblies.<name>.steps` in assembly order; a step has `part` (name, glob or list: one rigid group, e.g. a part with its sleeves) or `screw` (name, glob or list), `direction` (manifest-frame vector the part travels as it goes in, the part comes from final position minus t x direction; `"screw axis"` for screws), `seeded` and `derived`. Reorder, change a direction or delete `seeded` once confirmed. `base` lists parts present at the start. `checks/assembly_seed.py --name N --links L1,L2 --base PART` drafts a new chain from the connectivity graph (overwrites that assembly).

The first run after a part changes adds a few seconds for that part; a cold cache for the whole body costs about 2 minutes once. Solids come from the native STEP, and every cache (`.cache/work/cad-speed/cache`) is keyed by the sha256 of the file it was made from, so a regenerated STEP is never served stale. A part without a usable STEP is screened with its own mesh when that mesh is closed; only an open mesh (some covers) is voxel-filled, and a voxel fill can be ±50 % off the part's volume. The report lists every screening solid more than 5 % off its reference volume (`solid_volume_off_over_5pct`, also in the summary): the STEP volume with all solids fused, else the signed volume of the part's own closed mesh, else the recorded `volume_mm3`, which predates the ape-proportions morph of mesh-only shells and is then stale (each solid in the report names its `reference`); overlaps and distances against those are approximate. The summary also names neighbours screened as convex hulls (they over-state overlap). The gmsh calls stop themselves after `CAD_GMSH_TIMEOUT_S` (default 600 s for FEM meshing, 300 s for closed surfaces). A light iteration is `--parts NAME --checks geometry,mass,gaps,press,clearance` (about a minute); before showing a candidate add `--poses library`; `fit` and `fem` run once on the candidate you intend to show.

The robot BOM is the starting point for all hardware (owner 2026-11-20): `robot/body/bom/`. `build.py` generates it from the selected manifest, the hand-maintained `lines.json` (agents edit it: grouping of parts into buy / make lines, supplier, part number, price, notes, manual lines with no CAD, per-part overrides; its values win over the generated defaults) and `defects.json` (printed parts without a scripted STEP and what fixing each takes). Each line lists its parts with STEP and mesh (and how they resolve), the producer script and the command that regenerates it, the print setup (through `checks/process.py`), the hardware spec and the assembly steps. Output, recreated by the script: `.cache/work/bom/` `bom.json`, `bom.csv`, `BOM.md` (the builder's page), `dashboard-bom.json`; `--publish` writes the selected body's design-dashboard BOM and the robot planning BOM. `hardware.py` turns every screw, nut, washer and spacer into a buyable spec and generates its STEP / STL at the placement of the old mesh (fit to the old mesh reported). `inventory.py` is the per-part audit (where each file comes from, flags). `chain.json` / `rebuild_chain.py` record and rerun the builder chain that writes the selected manifest. The manifest carries no BOM of its own and `data/bom_groups.json` is gone; a study publisher that needs a BOM calls `build.design_bom_for(manifest)`.

Per-part settings are data in Git, `robot/body/checks/data/part_settings.json`, keyed by part name and set by whoever designs the part: `process` (printer, material, nozzle, layer height, print direction `up` in the manifest frame, `layer_normal_axes` kept as provenance and as the input of `--fem-variant studied_axes`, the FEM itself runs along `up`; resolved by `checks/process.py`: part setting, else the material's recommended nozzle, else the printer's defaults for that nozzle), `expected_hardware` (counts the checks compare with the manifest), `exact_fit`, `loadpath_slices` (set for the four R arm connectors, the four neck connectors and the torso chassis), `geometry_thresholds` (what the geometry check counts as an event; `_defaults` hold the old leg values, a part names only the keys it changes), `covers`, and `fem`. The material table is `data/materials.json` (manufacturer datasheet values; `legacy_*` entries only reproduce old study numbers), printers `data/printers.json`. A setup's wrench origin is data too: `origin_mm` is a point, `"load_centroid"`, or `{"joint": J | "joints": [A, B], "offset_mm": [...]}` derived from the manifest joint (midpoint of two for the pelvis), so it follows the part when joints move; the left arm connectors carry the mirror (x -> -x) of the right setups. `robot/body/checks/fem_evidence.py --study ID [--report REPORT]` prints the `run.py --checks fem,fem_setup` command of a published study (arm, neck-head, torso) and turns its report into `fem-evidence.json` in the study's artifact folder (recreated, not stored in Git); `--check-command` prints the geometry + clearance run that recreates the fit and CAD-rule sections. The publishers `robot/body/{arm,neck-head,torso}/publish_*_studies.py` build their records from these two reports (`--dry-run` prints the record, publishes nothing) and draw the FEM chart from `fem-evidence.json`; only materials the setups ran appear. A part's `fem` setup names its mesh size, supports, load patch, load cases (wrench at an origin, servo stall about a joint axis, head-wrench transfer), materials and bonded sleeves. Patches follow the part: surface in contact with a named mating part, or the part's own bolt holes near a mating part (format in the docstring of `robot/body/checks/fem_core.py`). Once a part has a setup, `fem` runs it whenever the part is in scope and `fem_setup` checks it against today's geometry; `--fem-variant`, `--fem-mesh-h` and `--fem-rigid-load` run comparison variants and mesh convergence. `--process KEY=VALUE` (repeatable: `nozzle_mm`, `layer_height_mm`, `line_width_mm`, `material`, `printer`, `up`) replaces the print setup of every printed part in scope for one run, to cross-evaluate another nozzle or material without changing the stored settings; the report records it. `robot/body/leg/fast_check.py` is the same tool as a short CLI for one leg part. `robot/body/leg/roll_flip_checks.py fit|press|fem` still write the roll-flip publication's report sections by calling the same checks.

For the low level training campaign, the lead agent coordinates the skill tracks and assigns individual training and independent challenges to agents through Idle. Evaluate progress qualitatively from observed motion, adaptation and recovery, including how and where behavior degrades. Judge every run, reward change and design change by agility across all motions. Show it as distributions over every evaluated motion, plus motions the controller has not trained on. The target motions are made-up stand-ins. Never plan a run or a change around one motion or one family; per-motion values only show where motion degrades. Keep distance, timing, contact and motor measurements as evidence, not binary training scores or promotion thresholds. Preserve historical frozen scores as provenance. Count simulator transitions, optimizer updates and distinct policies separately.

Across parallel simulation, aggregate continuous native-unit measurements into distributions and command-error accuracy curves by condition. Count world slots, episodes and independent start families separately. Keep early terminations and unrecovered events in view, and describe representative and severe trajectories in words rather than reducing them to a pass/fail or combined score.

Publish new training results as rows in `data/results.sqlite` with `infra/dashboard/results_hub.py publish` and upload selected MP4s to the existing private Infomaniak bucket with `infra/dashboard/results_hub.py upload`. The reusable viewer is `infra/dashboard/ui/`; extend it when a display pattern recurs. Do not generate a new HTML landing page, gallery, or standalone research note for each routine training run. Keep exact native reports, traces, source/config hashes, and decisive failures as compact evidence. Apply the regeneration cleanup rule to disposable derived outputs; hash-verify the bucket copy before evicting local evidence that must be retained. See `docs/operations/results-hub.md`.
