# Working rules

Operating procedures for agents in this repository. They follow the current tools and layout and change with them. The owner's intent and decision rules are in `AGENTS.md`.

Use idle tasks for work planning and the active goal for the objective. The 50 cm ape-shaped robot is the target; earlier 35 cm work is historical evidence. Microduck, Microban, and Berkeley are references. Use upstream Arena, Isaac Lab, Mimic, LeRobot, and GR00T code where relevant. Work locally in this folder; Runpod is compute only.

`robot/design.json` names the selected design: `selected` maps each robot section to its one selected study, and one study may cover several sections. Use its exact source when continuing; record a new selection with `infra/dashboard/results_hub.py select-design STUDY_ID --robot-section SECTION` and in Idle. Selection does not imply physical or learned-control qualification.

This is a disposable learning POC. Running the workflow is the test; do not add broad test coverage. Delete abandoned experiments when useful.

Git holds versions; file names never do. Edit a file and commit instead of creating `_v2`, `-r3`, `final` or dated copies, and name files by content. Process records (reviews, authorizations, verifications, receipts, handoffs, locks, logs, input snapshots) go to the Git-ignored `.bookkeeping/` folder, not `data/`. Research is one document per topic in `docs/research/`, updated in place with results; never a note per run. See `docs/operations/git-and-bookkeeping.md`; `.githooks/pre-commit` enforces the names (`git config core.hooksPath .githooks`).

The blob store, the private archive and the dashboards hold source of truth only: code and CAD sources in Git, external inputs that cannot be fetched again, and the current state the dashboards show (the selected design per section, the newest version of each skill with its clip) (owner, 2026-11-17). Everything else is recreated by running its script or its training when someone needs it, and is deleted at the end of the task from local disk and remote storage. Never upload derived outputs as backups. When a piece of work depends on something that cannot be recreated from a script, that is a defect: refactor it into a script plus its inputs while working on it.

Keep a lean local checkout: code, compact records and actual in-progress inputs. About 10 GB is a rough expectation, not an exact cap; preserve necessary working inputs and runtimes. Put temporary working materializations in `.cache/` or a temporary directory and evict them when the work ends. Remove unused reproducible tool installations and environments while keeping their pinned setup instructions. Do not retain historical run or design folders, locally or in object storage.

New producers must separate cheap derived output in `LAB_WORK_DIR` (`.cache/work/<run-id>/`) from retained native evidence in `LAB_EVIDENCE_DIR` (`artifacts/runs/<run-id>/`). Run them with `infra/lab storage run NAME -- COMMAND`, using `{work}` and `{evidence}` arguments or those environment variables. The wrapper records the exact command, seals completed evidence, hash-verifies private storage and evicts unchanged bulk automatically; successful scratch is disposable. Keep required inputs and compact configurations/reports outside scratch. Existing producers close one explicitly completed run with `infra/lab storage finish artifacts/EXACT_RUN` or `results_hub.py publish RECORD.json --close-run artifacts/EXACT_RUN`. Never close a run that still supplies active native inputs. `infra/lab storage sync` retries queued offloads; `clean` removes only declared completed scratch, never arbitrary `.cache` contents. See `docs/operations/storage-lifecycle.md`.

No simulation, training, evaluation rollouts or smoke tests run on the local CPU (owner, 2026-11-12). Smoke tests are short GPU jobs on the existing bounded serverless path, with their own spend reflection. Local work is code, reading, and analysis or renders of traces that already exist. Historical notes that describe "local CPU" checks are provenance, not a procedure to repeat. CAD verification (static FEM and kinematic collision sweeps) is the exception: it runs locally under `infra/tools/memguard.py` (owner, 2026-11-12).

CAD design loop (2026-11-18). One shared design check, `robot/body/checks/run.py`, replaces the per-study check scripts. Each design iteration runs it scoped to what changed and shows the owner a candidate only together with its findings; the whole body runs once before release to print. Run every heavy job under memguard with a timeout, so that a hang stops with a message. Heavy jobs may run in parallel (owner, 2026-11-20: "We shouldn't kill the computer but we should make use of the resources available"): the laptop has 32 GB and 10 cores, and a check or FEM job peaks at 1-2.5 GB on about one core. Budget: as many jobs as fit in memory, no job count (owner 2026-11-22): the memory the running guarded jobs hold plus the new job's `--limit-gb` at most 24 GB (8 GB stay for macOS and the apps); a job holds its full `--limit-gb` for its first 60 s, then the peak resident memory of its process tree so far; memguard enforces this itself: it waits until the job fits before starting the command, and a job starts ahead of the longest-waiting one only if that one still fits after it (no starvation of big jobs) (registry `~/.cache/memguard`, counting only real memguard processes, never shells whose command line mentions it), so start jobs directly and don't write your own `pgrep` wait loops (they count waiting wrappers and deadlock); `--no-wait` skips the wait. Use a fresh agent for each CAD step and don't resume a long one. Run long steps in the background and wait for the completion notice:

`python3 infra/tools/memguard.py --limit-gb 6 --timeout-s 900 -- .venv/bin/python -B robot/body/checks/run.py [--manifest PATH] [scope] [--checks a,b,c]`

`--manifest` is the body to check; without it the run uses `body_manifest` in `robot/design.json` (the selected body; the generators that write it are declared in the body definitions, and `robot/body/bom/rebuild_chain.py --dry-run` lists them in run order). Scope narrows the parts and combines with AND; none = every non-hardware part: `--parts NAME,GLOB` (part names or globs), `--section Hip` (robot section: the parts whose body definition declares `section: Hip`), `--link GLOB` (owning link), `--role ROLE`, `--changed-since REV|last-run` (Git revision, or file sha256 since the previous run on this manifest). The scoped parts are checked against their neighbours (close over the pose set or touching at standing), not against the whole body. `--checks` named = only those; none = every check that applies to the scope. `--list-checks` prints them. `--poses key|library|all|fit` picks the pose set (named data in `robot/body/checks/data/pose_sets.json`: key 23 key / extreme poses, library 151 realistic poses, all 223, fit the exact-fit list). Those are leg-motion sets; parts on an arm, neck or torso link get that region's own poses instead (`region_poses` in the same file: each joint at both ends of its manifest range, named combinations; `library` / `all` add the chain's corner combinations: arm 14 / 30 poses, neck 5 / 9, torso 30 / 42; a scope mixing leg and region parts gets both). The result is one JSON report, `.cache/work/cad-speed/checks/<label>/report.json` (`--label`), and a short worst-first summary on stdout: per check, per part, measurements in native units, worst cases with pose / location / mating part, counts of bad events, seconds. Lines that are context without a finding (the bed margin of a part that fits, STEP-vs-mesh volume difference) are kept in the report and only counted in the summary. The report carries `complete: false` (and `incomplete_running`, the checks under way) until the run's last write, so a killed or still running run never reads as finished; a new run under the same label deletes the previous report first. Setup timers (solids, neighbours) are repeated in every child process and reported apart (`setup_seconds_summed_over_children`), so `seconds` does not add them to the checks. `--changed-since last-run` names why a part was selected (`neighbour_changed: <part>` or `neighbour_never_recorded: <part>`). Nothing is pass or fail.

Editing the assembly order: the `assembly` section of the definition that owns the parts (`robot/**/<builder>.bom.yaml`): `subassemblies` (declared once: name, doc, `after` = subassemblies built before it and present at its start, `base`, `plan` = links / include / exclude / roles / mirror_of for the proposer) and `steps`, each with a unique `id`, its `subassembly`, `part` (name, glob or list: one rigid group, e.g. a part with its sleeves) or `screw`, `with` (nuts, washers, spacers, inserts and parts without geometry that go in with it, not measured), `direction` (manifest-frame vector the part travels as it goes in, the part comes from final position minus t x direction; `"screw axis"` for screws), `after` (the step ids before it, in any file) and `status` (`designer` or `seeded`). The order is the topological order of the `after` links; the check measures each step and ASSEMBLY.md shows whether the measurement supports it (not stored). `PYTHONPATH=robot/body .venv/bin/python -B robot/body/checks/assembly_seed.py propose [--names A] [--search]` (memguard, about 1 min / 4 GB) drafts steps for parts no step names, per owning file, into `.cache/work/bom/assembly-proposals/`.

The first run after a part changes adds a few seconds for that part; a cold cache for the whole body costs about 2 minutes once. Solids come from the native STEP, and every cache (`.cache/work/cad-speed/cache` of the main checkout, shared with the worktrees) is keyed by the sha256 of the file it was made from (a STEP without its header, whose FILE_NAME carries the export time: a rebuild of the same geometry keeps its caches), so a regenerated STEP is never served stale. A part without a usable STEP is screened with its own mesh when that mesh is closed; only an open mesh (some covers) is voxel-filled, and a voxel fill can be ±50 % off the part's volume. The report lists every screening solid more than 5 % off its reference volume (`solid_volume_off_over_5pct`, also in the summary): the STEP volume with all solids fused, else the signed volume of the part's own closed mesh, else the recorded `volume_mm3`, which predates the ape-proportions morph of mesh-only shells and is then stale (each solid in the report names its `reference`); overlaps and distances against those are approximate. The summary also names neighbours screened as convex hulls (they over-state overlap). The gmsh calls stop themselves after `CAD_GMSH_TIMEOUT_S` (default 600 s for FEM meshing, 300 s for closed surfaces). A light iteration is `--parts NAME --checks light` (15-20 s with warm caches, 2026-11-22); before showing a candidate run `--checks candidate --poses library`; `fit` and `fem` run once on the candidate you intend to show.

How a run behaves (2026-11-22, measured by `robot/body/checks/evaluate.py`). `--checks` takes check names and presets, mixed: `light` (geometry, mass, gaps, press, clearance), `candidate` (every per-part and standing check without fit, fem, the sweeps and the whole-manifest ones), `print`, `fasteners`, `motion`, `standing`, `all`; no `--checks` is `all` (on one part about 11 minutes and 5 GB, against 15-20 s for `light`). The first line on stderr is the plan: parts, checks, the time earlier reports on this machine suggest (median and p90) and, under memguard, how much of the timeout is left and which checks may not be reached; each check then prints when it starts and ends. A check that raises on some parts is rerun without them: those parts are listed in `failed_parts` with the exception and the code line, the others are measured (one missing STEP used to blank `holes` and `press` for every part in scope). A child that dies costs the check it was on; the group's other checks go on in a new child. 20 s before memguard's timeout the run stops itself: the report keeps every finished check, marks the one under way with the Python stack it was in (`stopped_in`), lists the ones not started, prints the summary and exits 124 (the same on SIGTERM or Ctrl-C). Labels are lower case (macOS paths ignore case) and held by one run at a time: a second run under a label in use stops at once and names the run that holds it; a run that replaces an earlier report under its label says which. On macOS a run keeps the laptop from idle sleep while it lives, but a closed lid still sleeps: memguard's timeout counts awake time only (a job is not killed on wake), and a run the laptop slept through says so (`slept_s` in the report and the summary; check and step seconds include the sleep: the assembly check's 1312 s of 2026-11-22 were 920 s and 238 s of maintenance sleep). `--changed-since last-run` with nothing changed exits 0 and says so. Manifest freshness: the plan prints, and the report keeps (`manifest_freshness`), every source a generator recorded in the manifest (path + sha256) that has changed since, and every upstream manifest of the body definitions' generator chain written after it: a checked body that lacks its upstream's changes says so (rerun the generators after it, `robot/body/bom/rebuild_chain.py --dry-run`). `--manifest` may name a file outside the repository (its part files stay repository-relative; the result cache is off for it). An overlap or distance measured against a voxel-filled or convex-hull screening solid carries `[approximate: ...]` on its summary line, and a STEP not used as the screening solid says why in the solid's description (a STEP that is the part moved names the offset). A check whose inputs have not changed since a stored result returns that result instead of running (`checks/resultcache.py`; the summary says `cached` and since when): the inputs are recorded while the check runs, every file it or its Python subprocesses read below the repository (manifest, STEPs, meshes, part settings, body definitions, data tables, the code it loaded), the set of body definition files and the run options; the result is reused only when each recorded file still has its sha256 (scratch manifests and STEPs under `.cache/work` are inputs like any other; only the checks' own cache folders are not). Failed results, failed parts and time-limited fit pairs are not stored; `--no-cache` (or `CHECKS_RESULT_CACHE=0`) runs everything. Stored results are shared by the worktrees like the other caches. The content-addressed caches (STEP tessellations, FEM meshes, closed solids, standard-part registrations) live in the main checkout's `.cache/work` and serve every worktree, written atomically (`checks/cachefs.py`; `LAB_SHARED_CACHE=0` keeps a checkout's own): a new worktree's first light + screws run took 337 s cold and takes 29 s shared. Make a worktree that runs the checks at once with `python3 infra/tools/worktree.py add NAME` (see Worktrees below). After changing the check tool itself, run `.venv/bin/python -B robot/body/checks/evaluate.py` in a worktree (some scenarios rewrite artifact files in place and refuse the main checkout) (`--list`; `--group speed|robust|truth`): real runs on the selected body and on copies with one injected fault (a part moved into its neighbour against exact OpenCascade truth, a STEP missing or truncated, a timeout, two runs on one label, a cold cache); results in `.cache/work/cad-speed/eval/results.json`.

The checks know no design (owner 2026-11-22: "the tests shouldn't know about the design, that gets fed in via the config"). Every fact about this robot comes from configuration or from the design data itself, never from a part, link or joint name: the body definitions (`robot/**/<builder>.bom.yaml`: kind, spec, settings blocks, and the relations `joined_to` {how: pressed}, `mirror_of`), the check tables in `robot/body/checks/data/` (materials, printers, tools, hardware, fit-class bands, pose sets, heat-source kinds, and `roles.json`: what a manifest role means where no definition says), and the manifest's geometry and joint tree. `robot/body/checks/relations.py` (`ctx.rel`) answers what a part is and how parts relate, in that order: definition, role table, geometry (the sleeve set whose sleeves touch a part, the part whose x-mirrored box matches, the joint whose origin and axis mirror a joint with its angle sign (a pair the joint table misses is declared in `pose_sets.json joint_mirrors`), limbs as the subtrees under the first mirrored joint, a joint's own servo as the servo case holding its origin (or `spec.servo_of_joint`)); `ctx.rel.source(part, what)` says which. A derived relation that is wrong is corrected by declaring it in the part's definition. Steering a run without editing the files: `LAB_DEFINITIONS_ROOT=<dir>` (another set of definitions), `LAB_PART_SETTINGS=<file>`, `LAB_CHECKS_DATA=<dir>` (another set of check tables); the result cache is off for such runs. The proof is `evaluate.py --only agnostic-renamed-joints-motion,agnostic-renamed-joints-fasteners,agnostic-renamed-joints-parts,agnostic-renamed-joints-fem,steer-definition-setting,mirror-leg-twin`: the same body with every part, joint and link renamed to an opaque id (definitions and tables renamed alike) must measure the same, and a setting changed only in a copy of the definitions changes the checks that read it and nothing else; the leg pose sets name one leg's joints and a scope on the other leg gets them mirrored through the joint tree (`mirror-leg-twin`: each left part measures what its right twin does).

Worktrees and the generator cache (owner 2026-11-22). Work that runs builders or checks goes in a worktree; what a worktree is for (a task, a section, anything) is the agent's choice; main stays open for small edits (docs, Idle bookkeeping). `python3 infra/tools/worktree.py add NAME` makes `../robot-learning-lab.worktrees/NAME` on branch NAME from main: `.venv`, `data`, `.tools` and `.artifact-store` linked (artifacts/ holds 229k links into it), `artifacts/` one APFS clone of main's (about 13 s for 111k files, no disk until a file changes, nothing written there reaches main); it prints what the other worktrees are changing, and `worktree.py list` shows every worktree's branch state, uncommitted files and the body files it changes. Bring a checkout's body up to date with `.venv/bin/python -B robot/body/bom/make.py` (`status` first shows what would run and why): it walks the declared generators in order and, for each, reuses the outputs of an earlier run from any checkout, branch or commit when every file that run read still has the same content here (recorded while it ran, `robot/body/bom/gencache.py`; STEP, npz and STL by content, not by header bytes), else runs it under memguard and stores its outputs; never copy artifacts between checkouts by hand and never run a chain step by hand to "refresh" the selected body. Section builders (`rebuild: false`) run only with `make.py --run ID`. When the work is committed, the worktree's own agent runs `python3 infra/tools/worktree.py land`: make in the worktree, then under main's land lock the merge into main (refused, changing nothing, when main has uncommitted edits in the branch's files or the merge conflicts), `make.py --report` in main (the selected body from the cache, then the BOM, the bom check and the BOM findings that changed, as scores), removal of the worktree and branch, and the cache gc. The cache keeps an entry while a live checkout holds it and for 3 days after it was last made or used (`make.py gc [--dry-run]`); derived outputs are never uploaded (owner 2026-11-22). A builder that edits a manifest another generator composes declares it as a `compose` entry in its own definition (`into` the stage, `call` script:function, `takes` parts | manifest, `after`, `needs`; `robot/body/bom/compose.py`), never as an import in the composing script.

The robot BOM is the starting point for all hardware (owner 2026-11-20): start page [robot/body/bom/README.md](../../robot/body/bom/README.md). What goes into it is the body's agents' decision, written in one annotated definition per builder next to its script, `robot/**/<builder>.bom.yaml` (schema `robot/body/bom/schema.json`; owner 2026-11-22): the builder's generators (command, inputs, outputs, `after`, resources), the manifest parts it owns and what each is (kind, BOM line, make / buy, quantity, spec, supplier and part number from a repo source or `unknown`, never guessed), its assembly steps, and its open defects. The BOM tool (`robot/body/bom/build.py`, `definitions.py`) has no knowledge of any part: it resolves the definitions against the selected manifest, adds file facts (how each STEP / mesh resolves, sha256, volume, mass, print setup) and writes `.cache/work/bom/` `BOM.md`, `ASSEMBLY.md`, `findings.json`, `bom.json`, `assembly.json`, `bom.csv`; `--publish` updates the design-dashboard BOM. What it cannot resolve is a finding naming the definition file to fix (the bom check lists them). When you add, change, rename or remove a part, screw or builder step, update your builder's `.bom.yaml` (nothing under `robot/body/bom/` changes), then rerun `build.py`, the assembly check and the bom check. `robot/body/bom/rebuild_chain.py` rebuilds the selected body in an isolated copy from the declared generators (order from their inputs and outputs), then runs those three steps and writes the design-dashboard record of the selected body to a file. The dashboard view of the selected body is generated from the same source (owner 2026-11-22, T-zmmdkm): `robot/body/bom/publish_body.py` (no part or study knowledge) builds it from a definition's optional `study` block (title, sections, summary, observation, measurements, limitations, statements, evidence and render links, scope), the manifest, every definition and the complete check reports on the same manifest sha256; publish it from the main checkout with `publish_body.py [--study ID] --publish` (it packages the display GLB when the manifest changed, under memguard; record sources must be committed). Never hand-edit a publisher after a redesign: edit the definition (parts, steps, study text). Drafting aids that never edit a definition: `checks/assembly_seed.py propose` (assembly steps) and `standard-hardware/propose_specs.py` (hardware specs). A study publisher that needs a BOM calls `build.design_bom_for(manifest)`; a new study is a `study` block published by `publish_body.py`, not a new publisher.

A part's settings live in its body definition (`robot/**/<builder>.bom.yaml`, on its `parts` entry: `process`, `expected_hardware`, `fit_classes`, `covers`, `exact_fit`, `loadpath_slices`, `geometry_thresholds`, `fem`, `edges`, `heat_source`, `section`: the robot section `run.py --section` selects by); the checks and the BOM both read it (owner 2026-11-22, T-ghvncz phase 2). `checks/ctx.py` overlays the definition over `data/part_settings.json`, which keeps the global keys (`_defaults`, `_printed`, `_core`) and what is not moved yet; each check report's `definitions` gives per part its definition file, entry and the source of every value, and every worst case names its definition. A value left in part_settings.json for a part whose definition carries that block is ignored and reported by the bom check (`setting_shadowed`). `robot/body/checks/move_settings.py --files F` moves a definition's remaining entries. Heat sources are declared per part (`heat_source: {kind}`); `data/heat_sources.json` keeps the kinds with their temperatures. Shared tables stay as they are: materials, printers, tools, fit-class bands, pose sets, Per-part settings are data in Git, `robot/body/checks/data/part_settings.json`, keyed by part name and set by whoever designs the part: `process` (printer, material, nozzle, layer height, print direction `up` in the manifest frame, `layer_normal_axes` kept as provenance and as the input of `--fem-variant studied_axes`, the FEM itself runs along `up`; resolved by `checks/process.py`: part setting, else the material's recommended nozzle, else the printer's defaults for that nozzle), `expected_hardware` (counts the checks compare with the manifest), `exact_fit`, `loadpath_slices` (set for the four R arm connectors, the four neck connectors and the torso chassis), `geometry_thresholds` (what the geometry check counts as an event; `_defaults` hold the old leg values, a part names only the keys it changes), `covers`, and `fem`. The material table is `data/materials.json` (manufacturer datasheet values; `legacy_*` entries only reproduce old study numbers), printers `data/printers.json`. A setup's wrench origin is data too: `origin_mm` is a point, `"load_centroid"`, or `{"joint": J | "joints": [A, B], "offset_mm": [...]}` derived from the manifest joint (midpoint of two for the pelvis), so it follows the part when joints move; the left arm connectors carry the mirror (x -> -x) of the right setups. `robot/body/checks/fem_evidence.py --study ID [--report REPORT]` prints the `run.py --checks fem,fem_setup` command of a published study (arm, neck-head, torso) and turns its report into `fem-evidence.json` in the study's artifact folder (recreated, not stored in Git); `--check-command` prints the geometry + clearance run that recreates the fit and CAD-rule sections. The publishers `robot/body/{arm,neck-head,torso}/publish_*_studies.py` build their records from these two reports (`--dry-run` prints the record, publishes nothing) and draw the FEM chart from `fem-evidence.json`; only materials the setups ran appear. A part's `fem` setup names its mesh size, supports, load patch, load cases (wrench at an origin, servo stall about a joint axis, head-wrench transfer), materials and bonded sleeves. Patches follow the part: surface in contact with a named mating part, or the part's own bolt holes near a mating part (format in the docstring of `robot/body/checks/fem_core.py`). Once a part has a setup, `fem` runs it whenever the part is in scope and `fem_setup` checks it against today's geometry; `--fem-variant`, `--fem-mesh-h` and `--fem-rigid-load` run comparison variants and mesh convergence. `--process KEY=VALUE` (repeatable: `nozzle_mm`, `layer_height_mm`, `line_width_mm`, `material`, `printer`, `up`) replaces the print setup of every printed part in scope for one run, to cross-evaluate another nozzle or material without changing the stored settings; the report records it. `robot/body/leg/fast_check.py` is the same tool as a short CLI for one leg part. `robot/body/leg/roll_flip_checks.py fit|press|fem` still write the roll-flip publication's report sections by calling the same checks.
